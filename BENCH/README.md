# Сравнение с референсом

Стенд работает в DOS и собирается тем же Turbo Pascal 7.0, что и игра. Игровые исходники `SRC/` он не изменяет. Обычная команда `BUILD` не включает ни таймер, ни счётчики.

## Запуск

Возьмите вторую копию проекта из исторической ревизии [`bbf628e`](https://github.com/pavel-voronin/kb2-restored/tree/bbf628eeb5af26786cedc55442243463e5ff731e). Это исходники референса, не его готовый EXE. Подключите эту папку как диск `D:`, а `continued` — как `C:`. Из корня `C:`:

```dos
BUILD
BENCH D:\
BRUN
```

`BENCH` сначала собирает неизменённый референс и сохраняет обычную сборку continued. Затем создаёт отдельные измерительные копии исходников в `BENCH/WORK/REF` и `BENCH/WORK/CUR`. Для каждой версии получаются две программы: измерение времени без счётчиков и подсчёт работы. Файлы ресурсов берутся из только что собранного `SRC/DIST/`.

Подготовку можно выполнять на быстром профиле эмулятора. Сам `BRUN`, включая `/QUICK`, запускайте на фиксированном профиле. При дополнительном запуске счётных программ на `dynamic / cycles=max` наблюдалась ошибка 200 до начала измерений; это записано отдельно как [B010](../BUGS.md). Из корня проекта на современном компьютере:

```text
dosbox-x -conf DOSBOX/BENCH.CNF
dosbox-x -conf DOSBOX/BLOW.CNF
```

Первый профиль делает пять временных повторов, второй — три (`BRUN /LOW`). Счётчики снимаются один раз: при фиксированных входах их значения детерминированы. Для короткой проверки есть `BRUN /QUICK` с одним временным повтором. Прогоны последовательно перезаписывают CSV в `BENCH/WORK/DATA/`: сохраните нужные результаты перед следующим запуском.

В конце `BRUN` вызывает `BREPORT`: программа проверяет отпечатки результатов, счётчики, выделение памяти и освобождение временных буферов, затем печатает медианы, минимум, максимум и изменение времени. Положительный процент означает замедление. Отпечаток результата должен совпадать также между временной и счётной сборками; проверяется устойчивость всех повторов. Отчёт можно вызвать отдельно из `BENCH/WORK/DATA` командой `..\..\BREPORT`.

В `WORK` находятся только генерируемые файлы. Их, EXE, TPU и журналы сборки не нужно добавлять в Git.

## Что измеряется

| Сценарий | Одинаковая работа в обеих версиях |
| --- | --- |
| `world0`…`world3` | Подготовка кампании, генерация мира и размещение героя; зерно `12345 + сложность`, одинаковое начальное состояние |
| `strikes` | 16 200 вызовов расчёта удара: 30×30 пар существ, три зерна, шесть ударов; фиксация результата каждой пары |
| `targets` | 11 200 поисков соседней цели, включая координаты за границей поля |
| `ai_scene` | Шесть подготовленных боёв, до двух фаз противника в каждом; зерно `42000 + номер сцены` |
| `tiles` | 500 выводов кадра 96×60 через `DrawPictureTile` |

Сценарии ударов и ИИ основаны на `TEST/TACTIC.PAS`. Это ограниченная нагрузка, а не полное прохождение игры. Новые сценарии можно добавлять в `BWORK.INC`.

`pit_ticks` — отсчёты системного таймера PIT с частотой 1 193 182 Гц: секунды = отсчёты / 1 193 182. `BCLOCK` читает BIOS-счётчик и защёлкнутый счётчик канала 0 с учётом ожидающего IRQ0. На время стенда PIT переводится в режим 2 с прежним делителем 65 536; после измерений восстанавливается режим 3. Обычная игра этим кодом не пользуется. Замеры одной серии должны завершаться быстрее получаса; одновременное стороннее перепрограммирование PIT не поддерживается.

Время включает подготовку входов внутри циклов ударов и поиска, а также запись результатов ударов в память. У ИИ измеряется только сам вызов фазы: загрузка картинок и подготовка сцены исключены. Игровые задержки и отрисовка внутри ИИ сохранены, поэтому его время не равно времени одного поиска пути. Подсчёт отпечатков и запись CSV находятся за пределами измеряемых интервалов, кроме простой общей суммы результата поиска. Стоимость двух чтений таймера не вычитается; нагрузки достаточно длинные, чтобы она была малой долей интервала.

`hash` — воспроизводимый 32-битный отпечаток, не криптографическое доказательство побайтовой идентичности. Проверяется состояние кампании, результаты ударов, состояние боевых сцен и все четыре плоскости скрытой видеостраницы после вывода кадров. Отдельные проверки `TEST` продолжают проверять генерацию, сохранения и боевые результаты.

Счётная сборка содержит 11 показателей:

| Поле CSV | Что считается |
| --- | --- |
| `strikes`, `damage` | Вызовы расчёта удара и применения урона |
| `targets`, `target_cells` | Поиски соседней цели и просмотренные кандидаты |
| `cost_cells` | Заполненные клетки таблицы стоимости движения ИИ |
| `frame_calls`, `frame_cells` | Полные проходы `FrameTerrain` и все посещённые клетки, включая пропущенные условием |
| `random` | Вызовы `Random` в игровой логике |
| `tiles`, `copy_bytes` | Вызовы вывода кадра и объём копирования через `CopyRecord` |
| `enemy_phases` | Фактически выполненные фазы ИИ |

Это выбранные счётчики работы, а не количество всех циклов программы и не количество инструкций процессора. Нули в обычной временной сборке означают отсутствие инструментации. Время счётной сборки для оценки скорости не используется.

## Память

`memory` — служебная строка CSV. Её поля после имени и нулевого номера: размер `Game`, запрошенная куча, фактическая занятая куча, её максимум, число выделений, свободная куча стенда и самый большой свободный блок; остальные поля зарезервированы. Временная сборка не перехватывает выделение: для кучи используйте `REFCNT.CSV` и `CURCNT.CSV`. Измеряется загрузка графических буферов до тестовых сценариев, а не максимум всех возможных игровых состояний.

Свободная куча измерительной программы зависит от её собственного кода, поэтому по ней нельзя оценивать расход обычной игры. `BREPORT` отдельно читает MZ-заголовки неизменённых `REFGAME.EXE` и `CURGAME.EXE`:

```text
минимум с PSP без кучи = размер EXE - размер заголовка + minalloc * 16 + 256
```

Там уже учтены данные и зарезервированный стек. Это минимальный блок загрузки, не фактический блок, выданный DOS: TP7 запрашивает всю доступную кучу. Графические буферы прибавляются отдельно. Зарезервированный стек — не измеренный максимум глубины вызовов. `heapcheck` показывает остаток временных выделений стенда; ноль означает, что его снимок кампании и буфер результатов освобождены.

## Эмуляция

Снятые серии используют DOSBox-X с `core=normal`, `cputype=286`, фиксированными 3000 или 700 cycles, 1 МиБ установленной памяти, EGA 256 КиБ и выключенными XMS/EMS/UMB. Для EGA нужны **оба** параметра: `vmemsize=0` и `vmemsizekb=256`; при `vmemsize=-1` второй игнорируется. Стенд проверяет объём EGA через BIOS перед запуском. Настройка звука отключена в стенде; правила игры не меняются.

[DOSBox-X прямо не обещает точность аппаратных тактов](https://dosbox-x.com/wiki/Guide:CPU-settings-in-DOSBox%E2%80%90X). Эти цифры пригодны для сравнения двух сборок при одинаковом бюджете эмулятора. Перевод `cycles` в МГц или PIT-отсчётов в реальные такты 286 из этих результатов не следует.

Для следующего уровня проверки подходит **86Box**: можно выбирать модель платы, процессор с частотой и задержки памяти 286/386. В [настройках машины](https://86box.readthedocs.io/en/latest/settings/machine.html) также доступны более точный режим PIT `Slow` и отключение менее точного движка 486 для 286. Предлагаемый начальный профиль: IBM AT 5170, 80286 8 МГц, один wait state, EGA 256 КиБ, 1 МиБ RAM, обычная DOS без менеджеров расширенной памяти, PIT Slow, синхронизация RTC выключена. Это выбранная испытательная конфигурация, а не найденные требования автора.

Этот же DOS-стенд можно перенести в образ диска 86Box и запустить без переписывания. Серия в 86Box пока не снята; образы BIOS и DOS в проект не добавлялись. Нет оснований обещать 100% соответствие каждого такта реальному AT: для этого нужна сверка с конкретной платой. [Bochs](https://bochs.sourceforge.io/doc/docbook/development/timers.html) привязывает таймеры к инструкциям и IPS, поэтому для проверки стоимости инструкций 286 он менее подходящий выбор.

## Результаты

Сырые CSV и сведения о сборках находятся в `RESULTS/`. Сравнение относится к структурному рефакторингу `0a8f9c6`, до каких-либо исправлений правил.

### Объём работы

Все показатели совпали между референсом и continued:

| Сценарий | Показатели |
| --- | --- |
| Каждый мир | 20 полных проходов FrameTerrain × 4 096 = 81 920 посещений клеток |
| Миры 0 / 1 / 2 / 3 | 30 871 / 34 200 / 37 089 / 37 615 вызовов Random |
| Удары | 16 200 расчётов и применений урона; 15 840 вызовов Random |
| Поиск целей | 11 200 поисков; 49 700 проверок клеток-кандидатов |
| ИИ | 11 фактических фаз; 810 клеток таблиц стоимости; 5 поисков цели и 45 кандидатов; 5 ударов; 22 вывода кадра |
| Графика | 500 выводов кадра |

В этих интервалах `CopyRecord` не вызывается: подготовительные копирования ИИ исключены, поэтому `copy_bytes=0`. Число проходов не уменьшилось. Небольшая разница скорости согласуется с изменением стоимости вызовов после выноса процедур и передачи контекста; это объяснение по структуре кода, не измерение стоимости каждой инструкции 286.

Совпали отпечатки всех восьми сценариев во всех временных повторах и в двух счётных сборках. Временные выделения стенда освобождены. Неизменённый референс, собранный перед инструментацией, даёт оригинальный SHA-256 `C24025EB398A1C4A960B4AB7A21ABB6FB81C86041F988178979381BFD8766A06`. Обычный EXE continued сохранил SHA-256 `719B50B00A253F85596AADBDA5369A9C48F3C55FA5DBA5AA56FCC24759845A0C`: игровые исходники при добавлении стенда не менялись. Хеши инструментов и шести EXE записаны в `RESULTS/META.CSV`.

### Время при 700 cycles

Медианы трёх повторов. Отпечатки совпали между версиями, повторами и серией 3000 cycles. Счётчики повторно на 700 cycles не снимались: при проверке этой серии использованы детерминированные значения из счётных прогонов на 3000 cycles. Обычный `BRUN /LOW` запускает также обе счётные программы на выбранном профиле.

| Сценарий | Референс, с | continued, с | Изменение времени |
| --- | ---: | ---: | ---: |
| world0 | 8.793047 | 8.793047 | 0.000% |
| world1 | 9.119089 | 9.119089 | 0.000% |
| world2 | 9.394796 | 9.394796 | 0.000% |
| world3 | 9.495287 | 9.495287 | 0.000% |
| strikes | 12.883513 | 12.907388 | +0.185% |
| targets | 3.988934 | 3.955888 | -0.828% |
| ai_scene | 16.169393 | 16.168951 | -0.003% |
| tiles | 2.237048 | 2.236907 | -0.006% |
Генерация сохранила прежнюю скорость; серия ударов медленнее примерно на 0,19%, поиск целей быстрее примерно на 0,83% на обоих ограничениях. Очень небольшую разницу времени вывода кадров не считаем обнаруженным ускорением: диапазоны повторов перекрываются.

Перед публикацией выполнена ещё одна сборка с нуля: все шесть EXE совпали с измеренными побайтово. Полный путь `BUILD → BENCH → BRUN /QUICK` прошёл в DOS, включая автоматическое сравнение. Отдельно проверено, что `BREPORT` отвергает намеренно изменённый счётчик и отпечаток в копиях CSV. Никакие исправления в игровые исходники не вносились.
